# 全栈网页应用管理平台 · 需求文档

> **本文档是本平台需求的唯一准绳，持续更新。** 规则：需求变更先改本文档（并在文末「变更记录」追加一行），再改实现；文档与实现不一致时，以文档为准修实现。
> 最后更新：2026-10-23 晚（持续维护）

## 1. 产品定位

- 给工作团队（组内同事）使用的网页应用管理平台，与家庭管理无关。
- 形态：中文自写外壳（门户 + 管理中心）+ PocketBase 安全内核；正式入口 https://app.example.com（单机部署，经隧道 / 反向代理对外）。
- 分工：其他 AI / 同事写好网页应用打包发来 → 平台维护者负责验包、部署、登记模板、挂门户、长期维护；平台层面的问题由维护者直接改。

## 2. 角色与账号

| 角色 | 说明 | 权限基线 |
|---|---|---|
| 超级管理员 | 平台维护身份（维护者），走 PocketBase 后台 | 全部（绕过业务规则） |
| 一级管理员 | 平台所有者 | 全局：所有门户、模板管理、用户与分组管理、审核 |
| 二级管理员 | 各组组长 | 门户管理仅限本组（见 3.2）；无模板管理 |
| 三级用户 | 普通同事 | 按门户/模板/项目的可见与编辑权限使用 |

- 注册采用「自助注册 + 管理员审核」：未审核账号可以登录，但看不到任何门户、模板与业务数据，也不能写入。
- 防提权：注册时夹带 level / approved / group 等字段一律被拒（接口层校验）。
- 账号安全：登录限流（连续错密码触发 429）；支持邮箱找回密码、自助改密；密码重置走平台 SMTP（发件显示名「全栈网页应用管理平台」）。

## 3. 权限模型（核心章）

### 3.1 可见性语义（门户与模板共用同一套）

每个门户、每个模板都带独立的可见性设置，四选一：

| 取值 | 谁能看到 |
|---|---|
| 所有人（all） | 全部已审核用户 |
| 指定组（group） | 与该资源所绑定的组相同的成员 |
| 指定人（users） | 名单（visible_user_ids）内的人 |
| 仅负责人 | 通过「指定人」且名单只含负责人实现：负责人能看，其他所有人都看不到 |

恒定规则：一级管理员总能看到全部；资源的负责人（owner）总能看到自己的资源。可见性在**接口层**强制（直调接口也拿不到），不是前端藏起来。

### 3.2 门户（pages）

- 门户出现在平台首页（门户），按 3.1 的可见性对每个用户过滤。
- **门户管理是治理视图**（2026-10-23 已定）：向管理员展示其管辖范围内的全部门户（含他人创建的），供编辑名称 / 权限 / 负责人、停用、移入回收站等治理操作；**门户管理不提供新建**——新建门户一律由用户在首页从模板生成（见 3.4）。门户管理对所有管理员开放（一级全局、二级限本组）。
- 二级建门户的限制：负责人必须是本人、只能绑本组、可见性只能是「指定组」、不能使用数据应用模式（app_mode）。
- 编辑 / 删除门户：一级任意；负责人本人；二级限本组门户。
- 删除先入回收站（软删），可恢复；彻底删
...[truncated 4411 chars]除在回收站里操作。
- 数据应用模式（app_mode）：需要读写平台数据的页面才启用；仅一级可建/可改（规则层拦截，二级夹带开启会被拒）。

### 3.3 模板库（templates）

- 模板是「图纸」，**不展示在门户首页**；首页只有用模板生成出来的门户。
- **模板管理页是只读清单**（2026-10-23 已定）：不存在个人或管理员在界面上建模板的情况——模板一律由维护者在部署应用 / 模板时登记维护；页面只列清单（名称 / 类型 / 说明 / 谁能用），不提供新建、编辑、删除入口。**唯一例外是「谁能用」**：它是权限设置，管理员可在清单里逐个调整（所有人 / 指定组 / 指定人）——因为并非所有模板都给所有人用。模板数据的接口增删改仍仅限一级（规则层）。
- **每个模板有自己的可见性**（语义同 3.1）：决定谁能在建门户时看到并使用这个模板。
- 模板分两类：内容模板（一整段 HTML 代码，套用时填入门户，可含 `__APP_SLUG__` 占位符）、应用模板（维护者已部署的应用，登记其地址，如 检查表）。
- 模板由一级「导入固定模板」维护；改模板不影响已经生成好的门户。

### 3.4 从模板新建门户（生成流程）

1. 在**平台首页**点「＋ 从模板新建」（管理中心不再提供新建入口）；
2. 模板列表**只列当前用户有权限使用的模板**；
3. 选中模板后**先弹出设置窗**，定：门户名称、标识、负责人、权限（所有人 / 指定组 / 指定人 / **仅负责人——其他所有人都看不到**）；
4. 确认后才生成门户并出现在首页（按所设权限过滤）；生成时把所用模板记到门户的 template 关联上，门户管理可按模板筛选查看。
- 接口层建门户约束：一级任意；二级仅限负责人本人 + 本组 + 组可见；三级负责人必须是本人、禁 app_mode、组可见时只能选本组（2026-10-23 随首页向导补齐——此前三级被建门户规则整段挡住，与「用户在首页自建」的定版冲突，已修复并验证）。
- 旧的「在编辑器里贴代码 / 套模板」方式保留，给一级做高级编辑用。

### 3.5 业务记录（app_data 与记账记录）

- 读：普通记录团队共享——已审核用户可读；项目制记录（检查表条目、记账本账目）按所属项目的可读范围在接口层过滤（见 3.6）。
- 写 / 删：记录的负责人本人、一级管理员，或所属项目编辑范围命中者。
- 记录建时必须把负责人盖成本人（防冒名）；前端按权限显隐按钮只是体验，强制在接口层。
- **记账本（2026-10-23 改项目制）**：记账本是应用模板（app-ledger），谁要用谁在 /jizhang.html 里自建记账本项目（名称 + 可读范围 + 编辑范围）；账目存 jizhang_records 并盖 project 关联，按项目权限收紧。旧的全员共享账本退出历史舞台，其遗留记录不属于任何记账本（project 为空），新界面不展示，接口层仍按旧的团队共享读保留，待定夺清理。

### 3.6 项目制（应用模板的数据模型）

- 应用模板每「建一个」就是一个**项目**：项目数据全部存平台数据库，不存浏览器本地。
- **项目权限分两套、互相独立**（2026-10-23 定版：「项目权限肯定要分，可读和可编辑」）：
  - **可读范围（read_scope）**四档：**全员可读 / 本组可读 / 仅负责人可读（仅自己可见）/ 指定人可读（多选，名单存 read_user_ids）**。决定谁能看到这个项目：不可读的人在项目列表里看不到它、打不开、导出不了，直调接口也是 404——项目行、项目内全部检查项、活动记录、附件都按项目的可读范围在**接口层**过滤。
  - **编辑范围（edit_scope）**四档：**仅负责人 / 本组 / 全员 / 指定人（多选，名单存 edit_user_ids）**。有编辑权的人保存即入数据库；正打开同一项目的其他人**自动刷新同步**到最新（实时推送 + 兜底轮询）。编辑范围同时决定项目内条目的编辑与删除权（删除规则与编辑规则一致）。检查项建时复制项目的范围与名单；在管理中心或项目列表改编辑范围时会级联同步到项目内各项。记账本的范围语义与此一致（3.5）。
  - 配置原则：编辑范围不应宽于可读范围（能改的人必须先能看）。历史项目可读范围为空时按「全员可读」处理（与拆分前的行为一致，不突然锁人）。
- 附件：单独存文件集合；上传者本人或一级可删；下载需登录令牌。**上传同样在接口层校验项目编辑权**：对项目没有编辑权的人直调接口上传也会被拒（2026-10-23 自查补上；附件的 project 字段为指向项目的关联字段）。
- 已落地应用：检查表应用（59 条标准检查项为种子，新建项目自动载入；附件 ≤9MB）；记账本（项目行 app='ledger'，账目在 jizhang_records 以 project 关联回项目，权限同项目制，2026-10-23 落地）。
- **项目导出**（2026-10-23 加）：在项目页或项目列表点「⬇ 导出」，生成一份**只读 HTML 存档**——导出时刻的数据快照（统计汇总 + 按分区表格 + 附件仅列文件名与大小），文件内无脚本、无输入框，填不了也改不了。

### 3.7 渲染与接口安全

- 普通门户页面一律在**沙箱 iframe** 中渲染（无同源权限），防止页面代码窃取登录令牌；只有 app_mode 页面同源渲染。
- 用户列表可见范围：一级全量；本人看自己；二级看本组。分组的增删改仅一级。
- 账号自改防提权（2026-10-23 自查发现并修复）：用户改自己资料时，接口层禁止变更 level / group / approved（曾存在「三级用户一条请求把自己提成一级」的漏洞，修复后自提权、自激活均被拒，普通改名等自助操作不受影响）；用户管理（改他人资料、审核、定级）由一级在管理端执行；账号删除仅一级。
- PocketBase 英文后台 `/_/` 公网可达（靠超级管理员强密码 + 限流），为已知接受项。

## 4. 功能清单（现状）

- 界面风格（2026-10-23 定版）：**扁平科技风**——深蓝 #0A2540 打底、青色 #22C3D6 点缀线、亮蓝 #2563EB 作链接/焦点色；白卡片细边框、无阴影、无渐变；门户 / 管理中心 / 登录注册 / 记账本等应用外壳统一。2026-10-23 晚参考组件化观感加了**主题层**（assets/theme.css + theme.js）：卡片柔和阴影与大圆角、统一焦点环；**主题色六选**（海蓝默认 / 青碧 / 翠绿 / 紫罗兰 / 蜜橙 / 玫红），每位用户在页面右下角 🎨 自行切换、按浏览器记住（localStorage pf_theme），只影响本人界面。

- 门户首页：按权限展示门户卡片；未审核账号显示待审核页。
- 管理中心（左栏）：门户管理（治理：总览全部门户、编辑 / 改权限 / 改负责人 / 回收站，不含新建）/ 模板管理（一级）/ 分组管理 / 用户管理（组织架构视图：待审核置顶、一级单独一支、按组展开、未分组兜底）/ 操作日志 / 站点设置；双登录（超级管理员页签、管理员账号页签）。新建门户在平台首页完成。门户管理除门户页面外，还治理**应用项目**（检查表项目、记账本）：改名、换负责人、改编辑 / 可读范围、级联删除。
- 记账本（应用模板）：自建记账本项目、进本记账——增删改查、分类汇总、回收站、CSV 导出，按项目的可读 / 编辑范围控制。
- 检查表应用：项目制协作（见 3.6）。
- 操作日志：记录走管理界面的关键操作（非全量审计）。
- 站点设置：平台名称（全栈网页应用管理平台，无副标题）。

## 5. 数据与运维

- 数据在 PocketBase 单机部署，每日自动整库备份，并同步一份异地副本。
- 超级管理员与应用账号凭据由部署者保管，不写进本文档。

## 6. 明确不做 / 已结案

- 某些企业内网打开平台出现 SSO 跳转循环（ERR_TOO_MANY_REDIRECTS）：为该网络的网关问题，与平台无关；此类网络需管理员加白名单后使用。
- 不做全站邮件转发。

2. **到期提醒（邮件）**：给资源/项目/条目设到期或节点日期，可配置「提前 N 天」自动发邮件提醒相关人（负责人等）。实现要点：需要定时任务扫描 + 走平台现有 SMTP 发送；提醒对象、重复提醒与已处理状态的规则待定版。
3. **审批人 / 审批流**：某些操作或内容可指定审批人，经审批后再生效（候选场景：项目结项、重要记录变更、门户发布等，范围待定版）。审批状态、驳回与留痕（接操作日志）的规则待定版。
4. **外部代码审计**：找其他 AI 以本文档为准绳复查实现——已定为暂缓，等上述功能成型后再做，避免对着半成品反复审。
5. **历史版本管理（2026-10-23 已定版，待实现）**：
   - **目标**：业务数据的每一次修改、删除都可追溯、可恢复——谁在什么时候把什么改成了什么，旧内容不丢。
   - **覆盖范围**：app_data 的业务记录（项目行、检查项、通用记录）、jizhang_records、pages、templates。不纳入：audit_logs（本身即日志）、app_data 里的活动流水行（checklist-activity，本身即流水）、users（账号变更看操作日志）。
   - **机制**：服务器端 PocketBase 钩子（pb_hooks）在记录 update / delete 时，**先把旧记录整条存入 history 集合再放行原操作**。前端不参与、绕不过；直调接口改数据同样留痕。
   - **history 集合字段**：目标集合名、目标记录 id、所属项目（关联，可空，冗余便于按项目查）、snapshot（旧记录完整 JSON）、action（update / delete / restore）、editor（操作者）、时间。
   - **可见与恢复**：历史的可见范围跟随目标数据本身——项目内记录的历史仅对该项目有可读权的人开放；恢复 = 把某条快照的内容写回目标记录，恢复人须对目标记录有编辑权；恢复前钩子会先快照当前版（action=restore），所以恢复本身可以反悔。
   - **入口（v1）**：检查表项目内查看检查项历史、记账本记录历史，均可一键恢复；其余集合先留痕，界面后补。
   - **保留上限**：每条目标记录最多留最近 **50** 个版本，超出删最旧；另设 **180 天**总保留期兜底；清理搭每日备份节奏在服务器端定时执行。
   - **附件**：只快照元信息（文件名 / 大小 / 上传者 / 时间），**不存文件二进制副本**。
   - **资源预算**：单条快照约 0.3–1KB，全平台封顶几十 MB 量级；不新增常驻进程，内存影响为零。
   - **与现有机制的关系**：操作日志记「谁在界面上做了什么」，历史版本记「数据的新旧内容」，互补；每日整库备份仍管灾难恢复，三者不互相替代。
   - **实现注记（2026-10-23 落地时定）**：钩子采用**请求级**钩子（onRecordUpdateRequest / onRecordDeleteRequest）——本机 PocketBase 的 JSVM 有个坑：钩子文件顶层定义的函数/变量在处理器执行时不可见（实测一调用即报错且不进 catch），故钩子逻辑必须全部内联在处理器内，维护时勿重构回顶层函数。请求级钩子覆盖全部界面与接口写入（含直调接口），且能拿到操作者与请求头（恢复标记头 X-History-Action；注意 requestInfo 里该头名为 x_history_action）。查看与恢复入口 v1 为独立页面 /history.html（检查表项目列表与记账本顶栏均有入口）。2026-10-23 晚后补**项目内入口**：检查表项目页左下胶囊「🕘 项目历史 / 🕘 本项历史」打开浮层（分别按 project、target_id 过滤，可直接恢复；只读成员仅查看），改着东西不用再跳页。
